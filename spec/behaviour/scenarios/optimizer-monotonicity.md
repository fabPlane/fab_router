# Scenario: the optimiser never makes the board worse

_generated by running both baseline routers as sealed programs on the board with the stated settings and recording what each produced: reference A was run twice per board through its command-line entry with identical settings (`maxPasses 100`, vias on, its fanout pre-pass on, which is the default of that entry), once with the post-routing optimiser on and once off; the two sessions were measured with the same ruler. In these command-line runs reference A added no Barrels on any board (see `spec/api/REVIEW.md` RV-23), so its Barrel columns are trivially equal. Reference B was run once and measured after its routing passes and again after its post-routing stage._

Required outcome (proposed contract clause R-6, see `spec/api/REVIEW.md` RV-19): with
`optimizerEnabled: true`, compared with the same run with `optimizerEnabled: false`,

- the number of Barrels added does not increase,
- the total Track length added does not increase,
- no connection that was complete becomes incomplete, and
- R-1 (no added violation) and R-2 (held items untouched) still hold.

Ruling: the spec follows reference A. An optimiser is a post-pass that may only shorten Tracks,
remove Barrels and straighten bends; anything that routes new connections belongs to the routing
passes and is measured there. Reason: the acceptance cases compare `traceLengthMm` and `barrels`
against reference numbers, and a stage that can lengthen the result would make those bounds
meaningless.
